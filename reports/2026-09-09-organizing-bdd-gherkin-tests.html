01Summary

Seven ecosystems, about a dozen reference projects (cucumber-*, Reqnroll, GitLab (Cucumber era), Sylius, Moodle, VCR, godog, behave, webdriverio-boilerplate…) converge on the same invariants. The ZSchool structure follows directly from them; no invention is needed.

Proposed decisions

  1. One single features/ tree at the monorepo root, one subfolder per PRD module code (adm…san) — the "functional area, grouped by capability" split that wins the official Cucumber review38 and already matches the PRD's own organization.
  2. One .feature file per FR-… requirement (the PRD's "Feature" block), never a file per scenario or per user story.
  3. Colocated pair <id>-<slug>.feature + <id>-<slug>.steps.test.ts — required by @effect-cucumber/vitest's loadFeature(import.meta.url) and confirmed by every ecosystem's own conventions.
  4. Glue shared by domain concept under features/support/ (steps/, layers/, fixtures/, hooks) via defineSteps — never step files that mirror a single .feature file.
  5. Traceability through tags: @FR-FIN-03, @INV-18, @PER-04, @PJ-DIR-01, version tags @mvp/@v1/@v2 — with a CI gate that counts coverage (the effect-cucumber pattern, validated by a Moodle-style .gherkin-lintrc).
  6. Everything in standard English Gherkin: normalized keywords (Feature, Background, Rule, Scenario Outline…), declarative style aligned with the PRD's own vocabulary. English is the domain-expert language for this project per the product owner's 2026-09-09 instruction (PROJECT.md v1.2) — see the note at the top of §5.6 for what that changed in this report.

02Method and scope

Scope. Only the organization of Gherkin specs (.feature) and the glue that exists solely for them (step definitions, hooks, support, fixtures): no unit-test layout, no CI beyond what enforces the structure.

Evidence. Every tree cited is verbatim (captured via the GitHub contents API / git ls-tree on 2026-09-09) or taken from the tool's official documentation; sources are listed in §10. ZSchool's own constraints come from STACK.md §8–§9 (runner @effect-cucumber/vitest 0.4, English .feature files, an ephemeral Neon branch per run, scenarios = the PRD's own acceptance criteria) and from prd/00-conventions.md (English, exclusive FR-<MOD>-NN IDs…, ASCII naming).

The decisive mechanical constraint. The chosen runner discovers nothing on its own: a test module calls loadFeature(path) at module scope, and the upstream repo's own convention resolves that path relative to the module via import.meta.url — so the spec and its glue form a colocated pair9. This is the exact equivalent of the generated code-behind sitting next to the .feature file in Reqnroll16, or the example.feature+example.spec.ts colocation in vitest-cucumber8.

03Ecosystem survey

For each ecosystem: the canonical structure (official templates), what actually forces it (file discovery, step binding), and known real-world projects.

TypeScript / JScucumber-js & the vitest ecosystem@cucumber/cucumber · @effect-cucumber/vitest

What forces the structure. The default discovery glob features/**/*.{feature,feature.md} (resolved from the project root) is the reason the features/ folder is everywhere. As long as specs live there, glue under features/ is loaded automatically (features/**/*.@(js|cjs|mjs)) — steps, hooks, and world require zero configuration. Spec language is set globally (language: "fr") or per file (# language: fr). In parallel, the unit of scheduling is the scenario (pickle), not the file: parallelism imposes no folder split1.

Playwright-BDD (features/ + steps/ per project, or a shared root tree in multi-project setups) and dogfooding amiceli/vitest-cucumber (colocated example.feature + example.spec.ts) round out the picture5 7 8. In monorepos, two placements coexist: features/ per package (dominant) or a shared root tree with per-project globs6.

The runner ZSchool has chosen: @effect-cucumber/vitest

No auto-discovery: loadFeature(path) is expected at module scope, binding one .feature to one describeFeature block; the repo's own convention is the colocated pair, and the project tests its own spec through *.feature + *.steps.test.ts pairs9. Distinctive traits: state via Effect Layers (shared per Feature / perScenario per scenario) instead of a mutable World object; reusable steps via defineSteps<R> modules; Gherkin tags → native vitest tags (@skip, @only, excludeTags); Rule extends the Layer; column-typed Scenario Outlines9 10. The parser ships the official French dialect too (dialect-fr.feature fixtures), for any future non-English module11.

.NETReqnroll (SpecFlow's successor)Reqnroll · MSTest/NUnit/xUnit

Context. SpecFlow (Tricentis) was pulled from GitHub; Reqnroll is its direct continuation (same v4 codebase, documented migration)19.

What forces the structure. .feature files can live anywhere in the project, but the documented convention is a Features/ folder (free-form subfolders). Each file compiles to a generated *.feature.cs test class placed right next to it — so the .feature file is the "test class" unit. [Binding] classes (steps, hooks, transforms) are assembly-global: placement under StepDefinitions/ is purely organizational; fine-grained targeting goes through [Scope(Tag=…)]. Language: #language: fr-FR per file or reqnroll.json → {"language":{"feature":"fr-FR"}}15 16 18.

Java / JVMCucumber-JVMcucumber-jvm · JUnit Platform · Serenity BDD

What forces the structure. .feature files are classpath resources discovered via @SelectPackages("com.example.project"): the canonical structure mirrors the glue package — src/test/resources/com/example/project/belly.feature ↔ src/test/java/com/example/project/StepDefinitions.java. Glue is declared by package (cucumber.glue=com.example.project) with name filters (.*StepDefinitions?|.*Hooks?) that make class suffixes a real convention. Parallelism is optional: the unit is the scenario/example, with tag-based locks22 23.

RubyOriginal Cucumbercucumber-ruby

What forces the structure. cucumber --init generates the world's canonical tree: features/step_definitions/ + features/support/env.rb (env.rb loads first, then every *.rb under support and step_definitions — file names are free, steps are global blocks)31.

Famous project #1 — GitLab (Cucumber era, v8.17): folders per domain (admin/ dashboard/ explore/ group/ profile/ project/ snippets/) plus flat top-level files (groups.feature, user.feature, search.feature); glue under steps/ mirrors the domains (steps/shared/, steps/project/); support: env.rb, capybara.rb, db_cleaner.rb. user.feature: one setup Background + ~7 @javascript scenarios segmented by role32. Famous project #2 — VCR: features/ organized as subject folders (cassettes/ configuration/ hooks/ record_modes/ request_matching/…) plus shared step_definitions/ and support/34. cucumber-ruby itself: features/docs/** mirrors the user manual chapter by chapter, glue lives in features/lib/35.

PHPBehat: Sylius & Moodle at scaleBehat 3/4

What forces the structure. behat --init generates features/bootstrap/FeatureContext.php (a PSR-0 autoload folder: support classes sit right next to it); behat.yml maps suites → paths + contexts36.

Famous project #1 — Sylius (major PHP e-commerce platform, Behat-first): features/ = one folder per domain (account/ cart/ checkout/ payment/ product/ shipping/…), verb-phrase file names (cart/viewing_total_quantity_of_the_cart.feature); and above all: the glue lives OUTSIDE the spec tree (src/Sylius/Behat/{Context,Page,Element} — page objects and elements); ~120 suite files by domain×layer (suites/{api,cli,domain,ui}/<domain>/<capability>.yml) filtered by tags like @shopping_cart&&@ui: the same spec tree serves every test layer37.

Famous project #2 — Moodle (the largest distributed .feature corpus known: 1,499 files): specs inside each component (mod/assign/tests/behat/: 62 files, mod/quiz/tests/behat/: 59…), specs and shared step classes centralized under lib/tests/behat/, and a root-level .gherkin-lintrc locking down style (no-dupe-feature-names, no-unnamed-features, outline-must-have-examples…)12 13.

The eight invariants

  1. One identifiable root folder holds every spec — features/ is the common denominator (default glob for cucumber-js/behave/godog, convention for Reqnroll, mirrored classpath in Java). Anywhere else always requires explicit configuration.
  2. Glue lives right next to the specs, never far away — step_definitions/, support/, bootstrap/, steps/: a sibling of the specs in every ecosystem; auto-loaded when it sits under features/ (cucumber-js).
  3. Splitting by functional domain wins at scale — GitLab, VCR, Sylius, Reqnroll.Specs, eugenp: one subfolder per functional area once the file count passes a handful; below that, flat is enough.
  4. "Functional area, grouped by capability" is the officially winning organization — the option the Cucumber review favors; Matt Wynne: it's the only one that doesn't let solution-domain vocabulary leak into the tree38.
  5. One .feature file = one capability (never a file per scenario, never per user story39); several scenarios per file; Background for shared preconditions; Scenario Outline + Examples for data variation.
  6. Glue is NOT a mirror of the spec tree — flat glue or glue organized by domain concept (Reqnroll.Specs, cucumber-js); steps tied to one specific feature are called out as an official anti-pattern41.
  7. Spec file naming: behavior names, snake_case (Java) or kebab-case (JS), sometimes verb-phrases (Sylius); glue files carry the subject name (cli_steps.ts, ShoppingSteps.java).
  8. Mature projects lock the style down — Moodle lints Gherkin in CI; effect-cucumber counts its requirement tags on every push; tags act as a cross-cutting index (view by module, by layer, by version)13 9 38.

05Writing a good Gherkin spec

A synthesis of the official sources (cucumber.io: the Gherkin reference, "Writing better Gherkin", anti-patterns, the #GivenWhenThenWithStyle blog series) checked against what the ZSchool PRD already does. Every rule is verifiable in the "do / avoid" blocks below.

On 2026-09-09 the product owner instructed that the whole project's documentation and specs move to English (PROJECT.md v1.2); this revision translates that decision through the report, including the worked examples in §7.4. 5.1 Describe behavior, not implementation

The foundational official rule: a spec describes the observable what, never the how. The test question: "would this wording need to change if the implementation changed?" — if yes, rewrite it40.

Avoid — imperative (UI-bound)

When I type "Fatima" into the field
  "guardian's first name"
And I click the "Save" button
Then I see the message
  "Guardian saved"

Do — declarative (functional requirement)

When the secretary adds a guardian
  to Youssef's enrollment file
Then the guardian appears on the file
  and receives an invitation by SMS

The imperative version breaks on the first screen redesign; the declarative version survives UI overhauls and reads as living documentation. This is exactly the documented failure of GitLab's "click-path" era33. ZSchool consistency: the PRD's own acceptance criteria are already declarative ("When the enrollment becomes ACTIVE…") — reuse them verbatim, never rewritten as UI gestures42.

5.2 The semantics of Given / When / Then

  • Given — the initial state of the world (data, context, permissions). No action.
  • When — a single meaningful action, the one the scenario is testing.
  • Then — the observable outcome for the actor; use concrete data ("ten installments of 1,200 DH"), never "it works" or "the system is correct".
  • And / But — to chain steps without disguised conjunctions (see anti-patterns §06).
  • 3 to 5 steps per scenario is the official comfort zone43.

5.3 Background, Rule, Scenario Outline: the three factoring tools

ToolUse it forOfficial guardrails
Background: The Given steps shared by every scenario in the file — the repeated "incidental details". Short (< 4 lines), lively, no complicated state; if it scrolls off screen, split the file; if it only applies to some scenarios, it doesn't belong in the Background43.
Rule: Group the scenarios of one business rule within a capability; carries its own Background, its own hooks, and (with effect-cucumber) can extend the Layer. One Background per Feature or per Rule — if two scenarios need different Backgrounds, they're different Rules or different files43.
Scenario Outline: + Examples: Collapses copy-pasted scenarios that differ only in values; the table edge: concrete, named examples. Never hide two different behaviors inside one outline; named Examples blocks (the cucumber-jvm calculator pattern); an outline with no Examples is a lint error (Moodle)24 13.

Avoid — outline hijacked (two behaviors)

Scenario Outline: Installment schedule
  Given an enrollment in state <state>
  When the installment schedule is generated
  Then <outcome>
  Examples:
    | state       | outcome                       |
    | ACTIVE      | ten installments created      |
    | closed      | an error is raised            |

Do — two named scenarios

Scenario: Generating the schedule for an active enrollment
  Given an ACTIVE enrollment
  When the installment schedule is generated
  Then ten monthly installments are created

Scenario: Generation refused for a closed enrollment
  Given a WITHDRAWN enrollment
  When the installment schedule is generated
  Then a "closed enrollment" error is raised

5.4 Steps: reusable, parameterized, in domain vocabulary

  • Organize steps by domain concept, never by .feature file ("feature-coupled step definitions", an official anti-pattern — an explosion of duplicated glue)41.
  • Parameterize variable values via cucumber-expressions ({string}, {int}, custom types {amount}, {moroccoDate}): one step definition, a thousand uses.
  • One step = one idea; two distinguishable assertions in the glue beat one "And" that hides a second one (the effect-cucumber repo's pattern: split explicitly so failures stay readable)10.
  • Test logic lives in services, not in steps — STACK.md §8: steps are thin adapters to domain services through Layers. This is the Effect-flavored version of the universal advice "keep bindings short, delegate to drivers/contexts" (the Reqnroll guide, Baeldung's ScenarioContext, Sylius page objects).
  • Avoid "I" and ambient actors: name the actor ("the secretary", "Khadija") — the PRD already does this, and the PER matrix makes the actor meaningful (permissions).

5.6 Gherkin's language support, and what ZSchool does with it

Gherkin is localized into 70+ languages, and the official guidance is clear: "the language of Gherkin should be the language of your domain experts"44. That is the reasoning the original draft of this report used to recommend French for ZSchool, since the PRD was French at the time. 5.7 Concrete data, independent scenarios

  • Concrete, meaningful data: "320 students including 4 duplicates", "1,200 DH", "+212661234567" — as the PRD already does. Vague values ("a few", "some data") make a failure impossible to interpret.
  • A scenario must be able to run alone: no ordering dependency between scenarios (the runner builds a fresh world per scenario — perScenario layer + an isolated TestClock9); state only flows through the Layer between steps (never a mutable closure — a dedicated gate enforces this in the effect-cucumber repo10).
  • Time determinism: every scenario gets a TestClock — scenarios like "September 5", "quiet hours 8pm–8am", "a started month still owed" become deterministic (STACK §8: DateTime always UTC, displayed in Africa/Casablanca).
  • The scenario title is a behavior sentence: "Mid-year arrival with the started month due in full", not "Installment test 3".

7.1 Place in the test pyramid

7.4 Full example — FR-FIN-03 "Installment schedule"

The first real file in the suite (FIN module, first vertical slice). The scenarios reuse the PRD block; the glue shows both levels: module-shared steps via use() plus steps specific to this file.

features/fin/fin-03-installment-schedule.feature
@FR-FIN-03 @mvp @fin
Feature: Installment schedule (MVP)
  Generated from the PRD acceptance criterion (prd/modules/16-finance-billing-collections.md §FR-FIN-03).
  Do not reword: this file is the execution of the PRD criterion.

  Background:
    Given a 2026-2027 fee schedule for 2AC with monthly tuition of 1,200 DH
    And an annual insurance fee of 150 DH

  Scenario: Ten-month installment schedule
    Given Youssef's enrollment in 2AC
    When the enrollment becomes ACTIVE on September 5
    Then ten monthly installments of 1,200 DH are created from September to June
    And a single 150 DH insurance installment is created on the activation date

  Scenario: Mid-year arrival with the started month due in full
    Given an enrollment activated on January 18
    When the installment schedule is generated with the default rule
    Then six monthly installments of 1,200 DH are created from January to June
    And the month of January is due in full

  Scenario: Mid-year departure
    Given an enrollment closed WITHDRAWN on March 12
    When the installment schedule is recalculated
    Then the unpaid installments from April to June are voided with a trace record
    And the March installment remains due in full and the balance survives the closure
features/fin/fin-03-installment-schedule.steps.test.ts
// Glue pair for FR-FIN-03. Steps shared across the FIN module live in
// `defineSteps` modules (support/steps/); this file keeps only the vocabulary
// specific to the installment schedule. Test logic lives in the SERVICES provided
// by the Layers — never in the steps themselves (STACK §8).
import { assert } from "@effect/vitest"
import { Layer } from "effect"
import { fileURLToPath } from "node:url"
import { describeFeature, loadFeature } from "@effect-cucumber/vitest"
import { installmentScheduleSteps, InstallmentSchedule } from "../support/steps/installment-schedule.steps.ts"
import { feeScheduleRegistryLayer } from "../support/layers/fee-schedule-registry.ts"

// The neighboring spec, resolved relative to THIS module — the pair survives any
// folder move (the effect-cucumber repo's own pattern).
const featurePath = fileURLToPath(new URL("./fin-03-installment-schedule.feature", import.meta.url))
const feature = await loadFeature(featurePath)

describeFeature(
  feature,
  // shared      : built ONCE per Feature — the fee-schedule registry is common.
  // perScenario : a fresh world per scenario — no enrollment leaks between scenarios.
  { shared: feeScheduleRegistryLayer, perScenario: InstallmentSchedule.layer },
  ({ Background, Scenario, use }) => {
    use(installmentScheduleSteps)  // shared steps for the "installment schedule" concept

    Background(({ Given }) => {
      Given("a {string} fee schedule for 2AC with monthly tuition of {int} DH",
        function*(year: string, amount: number) {
          yield* (yield* InstallmentSchedule).installFeeSchedule(year, amount)
        })
    })

    Scenario("Ten-month installment schedule", ({ Then }) => {
      Then("ten monthly installments of {int} DH are created from September to June",
        function*(amount: number) {
          const installments = yield* (yield* InstallmentSchedule).installments
          assert.strictEqual(installments.length, 10)
          // Two distinguishable assertions: the failure says WHAT didn't hold.
          assert.ok(installments.every((i) => i.amount === amount))
        })
    })
    // … every Scenario in the .feature file has its own block here (specific steps).
  },
  { excludeTags: [] }  // runner options (e.g. { excludeTags: ["@wip"] } in CI)
)
features/support/steps/installment-schedule.steps.ts — shared module for the domain concept
// Reusable steps for the "installment schedule" concept — imported by the FIN,
// TRA, DOC… pairs. The service requirement (InstallmentSchedule) is declared: a
// Feature whose Layer doesn't provide InstallmentSchedule can NOT use() this
// module (TypeScript error).
import { assert } from "@effect/vitest"
import { defineSteps } from "@effect-cucumber/vitest"
import { InstallmentSchedule } from "../layers/installment-schedule.ts"

export const installmentScheduleSteps = defineSteps<InstallmentSchedule>(({ Given, When, Then }) => {
  Given("{string}'s enrollment in 2AC", function*(student: string) {
    yield* (yield* InstallmentSchedule).preEnroll(student, "2AC")
  })

  When("the enrollment becomes ACTIVE on {string}", function*(date: string) {
    yield* (yield* InstallmentSchedule).activate(date)   // scenario TestClock: deterministic date
  })

  When("the installment schedule is recalculated", function*() {
    yield* (yield* InstallmentSchedule).recalculate()
  })

  Then("the month of January is due in full", function*() {
    const january = yield* (yield* InstallmentSchedule).installmentFor("January")
    assert.strictEqual(january.state, "DUE_IN_FULL")
  })
})
features/support/layers/fee-schedule-registry.ts — shared deterministic layer
// The `shared` layer: an in-memory fee-schedule registry for FIN scenarios.
// Real-database variant: the same interface, backed by a Layer wired to the
// run's ephemeral Neon branch (migrations + fixtures) — see STACK §8.
import { Context, Effect, Layer, Schema } from "effect"

export class FeeSchedule extends Schema.Class<FeeSchedule>("FeeSchedule")({
  year: Schema.String, monthlyTuition: Schema.Number, annualInsurance: Schema.Number,
}) {}

export class FeeScheduleRegistry extends Context.Service<FeeScheduleRegistry, {
  readonly feeSchedule: (year: string) => Effect.Effect<FeeSchedule>
}>("FeeScheduleRegistry") {
  static readonly layer = Layer.effect(this, Effect.gen(function*() {
    const schedules = new Map([["2026-2027", new FeeSchedule({ year: "2026-2027", monthlyTuition: 1200, annualInsurance: 150 })]])
    return FeeScheduleRegistry.of({ feeSchedule: (year) => Effect.sync(() => schedules.get(year)!) })
  }))
}

7.5 Wiring vitest & the traceability gate

vitest.config.ts (root) — two projects, one run
// Vitest 4: projects. The .feature files are NOT test targets themselves — only
// the *.steps.test.ts pairs are (the parser loads them via loadFeature).
import { defineConfig } from "vitest/config"

export default defineConfig({
  test: {
    projects: [
      { test: { name: "unit", include: ["packages/*/src/**/*.test.ts"] } },
      { test: { name: "bdd",   include: ["features/**/*.steps.test.ts"],
                typecheck: { enabled: true } },  // the Layers' compile-time guarantee
      },
    ],
  },
})
scripts/verify-bdd-traceability.ts — every scenario-bearing PRD requirement is covered (the effect-cucumber pattern)
// 1. Extract the IDs from the PRD's ```gherkin blocks → FR-*, PER-*, INT-HEB-01…
// 2. Extract the @ID tags from features/***.feature
// 3. Fail if a PRD ID has no matching tag, or a tag matches no PRD ID.
// Run on every push — the same mechanism as the effect-cucumber repo's own
// "traceability check", which counts its acceptance-requirement tags.

On top of that, a Moodle-style Gherkin lint (.gherkin-lintrc: unique feature names, outlines with Examples, named files) locks down the §05 style in CI13.

7.6 Database per run — where it plugs in

No layout surprise here: the database glue lives under features/support/ and is injected like any other Layer.

  • support/layers/db.ts — a Layer that reads NEON_TEST_BRANCH_URL (created by the pr-N Alchemy stage), applies the packages/db migrations, then the fixtures; provided as shared to every feature that touches the database.
  • support/hooks.ts — AfterAllScenarios: keeps the branch on failure (for diagnosis), destroys it otherwise (STACK §8).
  • Permission scenarios (cross-cutting/per/) rely on @qadi/testing's deterministic Layers — reproducible decisions, no database needed.

08Alternatives considered and rejected

OptionObserved inReason for rejection, for ZSchool
Specs per package (packages/x/features/) Moodle (specs inside each component), the dominant pattern in JS monorepos6 ZSchool requirements are cross-cutting across packages (one FR-FIN-03 spans domain+db+api); the natural split is the PRD business module, not the technical package. STACK §9 already settled this: features/ at the root.
Keyword-centralized glue (given.ts/when.ts/then.ts) webdriverio-boilerplate4 Orders glue by syntax, not by domain: at 258 FRs, each file becomes a catch-all. Glue organized by domain concept (installment-schedule.steps.ts) stays greppable and reusable. (The runner has no auto-loading anyway, so a keyword split adds nothing.)
A step folder that mirrors the spec tree GitLab v8.17 (steps/project/ ↔ project/)32 Revives the feature-coupled-steps anti-pattern41; Reqnroll.Specs' flat glue holds up better at scale. For ZSchool, the colocated pair already covers file-specific vocabulary; anything shared goes in support/steps/.
One .feature file per scenario never observed in the projects studied A documented anti-pattern (disposable files, duplicated Background); the PRD's per-FR block is already the right capability-level granularity38 39.
Writing specs in French or bilingual this report's own original 2026-09-09 draft The official rule — the domain experts' own language44 — pointed to French while the PRD itself was French. The product owner's 2026-09-09 instruction moved the PRD, this report, and the whole project to English (PROJECT.md v1.2); under the same rule, that now means standard English Gherkin, with no # language: header.
